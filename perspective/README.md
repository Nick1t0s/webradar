# Native perspective window

Отдельное Python/Tk-окно: белое поле и каркасные прямоугольные тела игроков
в перспективе главного игрока. Цвета союзников и врагов задаются в настройках.
Центральный прицел отключён. Карта не загружается.
Это подписчик существующего WebSocket helper, без собственного чтения памяти.
Браузер и Vite для этого окна не нужны.

## Контроль отдачи: Linux / Hyprland

В управляющем окне нажмите **Контроль отдачи…**. Выберите физическую мышь,
укажите текущую `sensitivity` из CS2 и разрешите компенсацию. Она остаётся
на паузе до нажатия **Mouse4** (можно выбрать Mouse5) в активной CS2.
После переключения отпустите ЛКМ, затем удерживайте её для компенсации.
Состояние видно в управляющем окне; при прямом запуске `--overlay` — в stderr.
Оверлей для работы компенсации включать необязательно.

Модуль только читает состояние двух кнопок выбранной мыши и посылает
относительные движения через `/dev/uinput`. Он не записывает память CS2,
не нажимает кнопки, не захватывает мышь и не читает клавиатуру.
Боковая кнопка продолжает поступать в игру: не назначайте ей другое игровое
действие, если оно мешает переключению.
Использован стандартный [интерфейс uinput ядра Linux](https://docs.kernel.org/input/uinput.html).

Нужны Python-зависимости из `perspective/requirements.txt`, включая Pydantic 2.
Устанавливайте их в отдельное окружение перспективы. На Linux системные
GTK/PyGObject/Cairo доступны через `--system-site-packages`; новые Python-пакеты
устанавливаются только в это окружение:

```sh
python3 -m venv --system-site-packages perspective/.venv
perspective/.venv/bin/python -m pip install -r perspective/requirements.txt
./perspective/run-linux.sh
```

Обычное окно использует Tk из Python. Нативному оверлею дополнительно нужны
GTK/PyGObject/Cairo, описанные ниже. Никакие зависимости автоматически не
устанавливаются; существующий `helper/linux/.venv` может не содержать Pydantic.

Нужны права **чтения только выбранного event-устройства** и записи в `/dev/uinput`.
Приложение не запускается через sudo и само не меняет права устройств.
Временный доступ к текущему узлу мыши можно выдать отдельно:

```sh
# Замените event24 текущим узлом выбранной мыши из списка в интерфейсе.
sudo setfacl -m "u:$(id -un):r" /dev/input/event24
sudo setfacl -m "u:$(id -un):rw" /dev/uinput
```

ACL исчезнет после пересоздания устройства. Bluetooth-мышь сохраняется по
её идентификатору; после переподключения программа найдёт новый event-узел,
но права на него могут потребовать повторной выдачи. Ошибки доступа видны в
строке состояния и не мешают просмотру перспективы.

Используется только helper на `localhost`, loopback IPv4 или IPv6. Выбранный
игрок должен быть живым локальным игроком helper; профиль чужого игрока
не управляет вашей мышью. Нужны свежие кадры не старше 250 мс и активная,
разблокированная CS2. Фокус проверяется каждые 50 мс, кнопки — примерно каждые
8 мс. После потери этих условий, смены оружия, задержки обработчика больше
50 мс или переключения компенсации требуется отпускание ЛКМ перед новой
очередью. При запуске, изменении настроек и восстановлении устройства модуль
снова на паузе. Одновременно работает только один исполнитель: окно перспективы
и оверлей используют пользовательскую блокировку в `XDG_RUNTIME_DIR`.
Остальные окна показывают его актуальное состояние (пауза, готовность,
компенсация) из атомарно обновляемого файла статуса в том же каталоге.

Профиль выбирается по `m_weapons.m_active` из существующих данных helper.
Начальные профили `ak47`, `m4a1` (M4A4) и `m4a1_silencer` (M4A1-S) —
**приблизительная вертикальная компенсация для калибровки**, а не измеренные
паттерны CS2. Для других оружий движения нет. JSON профилей можно изменить в
том же диалоге; неизвестные поля и некорректные значения отклоняются до сохранения.

Каждый участок содержит `duration` в секундах и скорости `x`, `y` в отсчётах
мыши в секунду при sensitivity=1. Положительный `x` двигает вправо, `y` — вниз.
Результат умножается на `strength / sensitivity`; дробные отсчёты сохраняются
между тактами, поэтому скорость не зависит от частоты кадров. По окончании
профиля движения прекращаются до следующей очереди. Пример одного профиля:

```json
{"ak47": [{"duration": 0.1, "x": 0, "y": 0}, {"duration": 2.9, "x": 0, "y": 80}]}
```

Калибруйте силу и участки на локальной тренировке. DPI/ускорение виртуальной
мыши и внутриигровые настройки тоже влияют на результат. Компенсация запускается
по удержанию ЛКМ: текущий протокол не сообщает о фактическом выстреле,
перезарядке, открытом игровом меню или пустом магазине. Случайный разброс и
восстановление отдачи между короткими очередями не вычисляются.

Здоровье показано по принципу радара: цвет игрока занимает нижнюю часть каркаса
пропорционально HP, а недостающее здоровье — белую верхнюю часть. При 100 HP весь
каркас цветной; при 25 HP цветной остаётся нижняя четверть. Разделение остаётся
горизонтальным при взгляде вверх/вниз. Чёрная обводка сохраняет видимость белых
участков в обычном окне и поверх светлой карты. Внутри каркасов оверлей остаётся
прозрачным; центральный прицел не возвращается. Используется существующее
`m_health`, без изменений helper. Недоступное или некорректное значение HP
отображается полным цветом, как на радаре; значения ограничиваются диапазоном 0–100.

## Прозрачный оверлей поверх CS2: Linux / Hyprland

В обычном окне нажмите **Включить оверлей поверх CS2**, затем переключитесь в игру.
Управляющее окно сохраняет выбор игрока и настройки; оверлей подхватывает изменения
автоматически. Кнопка **Выключить оверлей** или закрытие управляющего окна завершает
созданный им процесс оверлея.

Можно запустить только прозрачный слой с уже сохранёнными настройками:

```sh
./perspective/run-linux.sh --overlay
```

Остановить такой запуск можно `Ctrl+C` в его терминале.

Оверлей работает нативно через **Wayland + GTK3 + gtk-layer-shell**, без XWayland.
Поверхность имеет альфа-канал и находится на слое `OVERLAY`, над полноэкранной
игрой. Мышь и клавиатура проходят в игру; слой не запрашивает фокус и не занимает
место в раскладке Hyprland. Конфигурацию compositor приложение не изменяет.

Слой показывается только при активном окне с классом `cs2`, `cs2.exe` или
`steam_app_730`. Если активны PyCharm, терминал или другое приложение — слой скрыт.
Монитор и положение окна игры определяются через read-only `hyprctl` IPC.
Учитываются логические координаты, масштаб и поворот монитора. При выходе из игры,
потере данных или исчезновении выбранного игрока рамки не остаются на экране.

Фон, включая свободные поля вокруг изображения, полностью прозрачен. Тела
рисуются цветами союзников/врагов с чёрной обводкой, без прицела. Оверлей совмещается со **всей
игровой областью**; множитель уменьшения применяется только к отдельному окну
перспективы. Для совпадения с картинкой выберите игрока, из чьих глаз показана CS2.
Существующие ограничения реконструкции камеры перечислены ниже.

В настройках есть **Оверлей: CS2 растягивает картинку на всё окно (без полос)**:

- Выключено: сохраняются пропорции разрешения CS2, проекция учитывает поля
  по краям. Сам оверлей не закрашивает эти поля.
- Включено: проекция растягивается на весь прямоугольник игры. Это нужно,
  например, для 4:3 stretched. Настройка не изменяет графику самой CS2.

Для оверлея нужны `hyprctl`, GTK3, PyGObject, Cairo и typelib `GtkLayerShell-0.1`.
На этой машине GTK3, Python bindings и библиотека уже были установлены; недостающий
typelib подготовлен локально в `perspective/.runtime/girepository-1.0` из
дистрибутивного пакета той же версии, без установки системных Python-пакетов.
Этот локальный runtime не отслеживается Git. На другой Ubuntu-системе пакет
typelib называется `gir1.2-gtklayershell-0.1`; соответствующая системная библиотека —
`libgtk-layer-shell0`. Обычному Tk-окну эти дополнительные зависимости не нужны.
Если Python из собственного окружения не видит уже установленные GUI bindings,
выберите подходящий интерпретатор через `PYTHON` в команде запуска.

Лог процесса, запущенного кнопкой, находится в `perspective/.runtime/overlay.log`.
## Прозрачный оверлей на Windows

Выполните `perspective\run-windows.bat` и нажмите **Включить оверлей поверх CS2**,
либо запустите только слой: `perspective\run-windows.bat --overlay`.
Используются стандартные Tk и Win32 API через ctypes; GTK и Wayland не нужны.
Поддерживаются Windows 10/11 и оконный либо оконный полноэкранный режим CS2.
Работа поверх эксклюзивного полноэкранного режима не гарантируется.

Слой прозрачен и пропускает мышь и клавиатуру в игру, не забирая фокус.
Он следует за клиентской областью активного процесса `cs2.exe`, учитывает DPI
и положение мониторов. При переключении на другое приложение, сворачивании игры,
потере связи или устаревании кадров рамки скрываются. Выбор игрока, цвета,
настройки камеры и адрес источника общие с управляющим окном.
Linux сохраняет отдельный нативный Wayland/GTK backend; проекция и состояние
получаемых данных используются совместно.

## Источник данных и подключение

В управляющем окне всегда показан **Источник данных**. Кнопка **Подключение…**
открывает поле **Источник данных (WebSocket helper)**. Укажите полный адрес
компьютера, на котором работает helper, например:

```text
ws://localhost:22006/cs2_webradar
ws://192.168.1.20:22006/cs2_webradar
```

Первый адрес подходит для helper на этом компьютере, второй — для другого
компьютера в сети. Для защищённого WebSocket-сервера используется `wss://`.
HTTP сайта на порту `5173` и WebSocket данных на порту `22006` разделены;
нативный оверлей подключается к WebSocket напрямую и не требует сайта.

Адрес хранится в явном поле `ws_url` файла `perspective/settings.json`.
Изменение через интерфейс сохраняет его, очищает предыдущую сцену и запускает
новое соединение; запущенный оверлей подхватывает тот же файл автоматически.
Режим `--overlay` читает этот файл без управляющего окна. Неверный протокол,
некорректный порт, пробелы, пароль и фрагмент URL отклоняются до соединения.

Настройки источника в браузерном радаре и миникарте находятся в **Settings →
Data source (WebSocket)**. **Connect** сохраняет адрес отдельно от профилей
игроков и переподключает клиент; **Use default** сбрасывает его.
Приоритет: сохранённый адрес → `VITE_WS_URL` → имя компьютера из адреса сайта,
порт `22006`. Настройки браузера независимы от `perspective/settings.json`.
Защита helper проверяет Origin браузера: по умолчанию сайт и источник данных
должны использовать одинаковое имя компьютера, хотя порты различаются.
Нативный клиент заголовок Origin не отправляет.

## Запуск

1. Перезапустите **обновлённый** helper обычным способом. Старый процесс не начнёт
   передавать новые поля без перезапуска. Радар и другие его режимы остаются доступны.
2. Из корня репозитория выполните:

   ```sh
   ./perspective/run-linux.sh
   ```

   Скрипт использует `perspective/.venv`. Если его нет, выбирает существующий
   `helper/linux/.venv`, затем системный Python.
   `PYTHON=/путь/к/python ./perspective/run-linux.sh` выбирает другое окружение.
   Новые окружения и пакеты этот скрипт не устанавливает.

   На Windows: `perspective\run-windows.bat`. Python должен иметь установленную
   зависимость `websockets` из helper. Также нужен Tk: он обычно включён в установщик
   Python для Windows; на Linux нужны доступные Python-привязки Tcl/Tk.

   Эквивалентный запуск с готовым окружением: `python -m perspective`.
3. Выберите главного игрока в верхней панели. Изначально выбран игрок,
   отмеченный `m_is_local` у helper. Для независимого выбора используйте конкретного
   игрока из списка. Выбор сохраняется по Steam ID; при выходе игрока окно ждёт
   именно его, а не переключается на другого.

## Камера и настройки

При первом запуске создаётся локальный `perspective/settings.json` по
`config.example.json`. Его можно менять через кнопку **Настройки** или вручную
при закрытом окне. Настройки CS2 приложение только читает.

- **Разрешение:** `setting.defaultres` и `setting.defaultresheight` из
  `userdata/<account>/730/local/cfg/cs2_video.txt`. Автопоиск учитывает Steam на Linux,
  Flatpak/Snap, переменные `STEAM_DIR`/`STEAM_ROOT`/`STEAM_HOME` и Windows-реестр.
  При нескольких аккаунтах выбирается совпадающий Steam ID; при неоднозначности
  выберите папку `cfg` в настройках. Доступны явные ширина и высота.
  Пока нет свежих данных выбранного живого игрока, окно показывает состояние
  подключения или сообщение helper вместо ошибки выбора cfg. Когда игрок появляется,
  профиль выбирается по его Steam ID; разрешение проверяется для этой камеры.
- **Камера и FOV:** для выбранного локального игрока helper автоматически
  используется его действующая `m_view_matrix`. Она задаёт положение камеры,
  направление и масштаб проекции; сохранённый FOV из cfg в этом режиме не влияет
  на рамки. Строка состояния показывает **матрица игры** и эквивалентный FOV при 4:3.
  Ручной FOV имеет приоритет и отключает матрицу. Для другого выбранного игрока,
  старого helper без матрицы или некорректной матрицы используется реконструкция:
  ручное значение, затем `m_camera_fov` выбранного игрока, затем сохранённый
  `default_fov`/`fov_desired` из `cs2_machine_convars.vcfg` и
  `cs2_user_convars_0_slot0.vcfg`.
  Сохранённый convar может отличаться от реально применённого игрой: источник
  показан в строке состояния. Если FOV не найден, окно просит ввести его.
  Это горизонтальный FOV **при 4:3**: при другом формате он пересчитывается
  с сохранением вертикального обзора. `viewmodel_fov` не используется.
- **Множитель размера:** `0.5` означает поле в половину ширины и высоты разрешения
  CS2. Кнопка **Размер × масштаб** также запрашивает соответствующий размер окна.
  Если места меньше, поле дополнительно уменьшается целиком без обрезки.
- **Hyprland:** используется обычное непрозрачное Tk-окно через XWayland.
  Даже если compositor принудительно растягивает окно, белое поле сохраняет
  пропорции CS2 и ограничение размера по множителю. Свободное место — чёрные полосы.
  Правила floating для Hyprland не обязательны.
- **Цвет союзников / Цвет врагов:** поля `teammate_color` и `enemy_color` принимают
  `#RRGGBB`; в настройках есть выбор цвета через палитру. По умолчанию используются
  зелёный `#4ade80` и красный `#ef4444`. Цвет определяется относительно команды
  выбранного главного игрока. Настройки применяются и к отдельному окну, и к оверлею;
  оверлей подхватывает сохранённые изменения без перезапуска.
- **Высота глаз и размеры тела:** берутся из новых полей helper, если доступны.
  Иначе используются явно заданные `eye_height`, `body_width`, `body_height`;
  строка состояния сообщает о таком приближении. Стандартные значения шаблона:
  64, 32, 72 игровых единицы. Для точной проекции приседа нужны живые данные helper.
- **Лучи взгляда:** `show_view_rays` включает их по умолчанию в окне перспективы
  и обоих нативных оверлеях. Лучи других живых игроков начинаются от глаз,
  учитывают горизонтальный и вертикальный угол и имеют длину 1024 игровых единицы.
  Цвет совпадает с цветом команды и не зависит от здоровья. При отсутствии
  вертикального угла луч пропускается; при отсутствии позиции глаз используется
  `eye_height`. Луч выбранного игрока не рисуется. Стены лучи не обрезают.
- **Другой helper:** измените `ws_url`, например на
  `ws://192.168.1.10:22006/cs2_webradar`. Окно ничего не отправляет helper и не
  меняет общие настройки радара. Для удалённого игрока укажите его графические
  параметры вручную либо выберите доступную локальную копию его `cfg`.

Разрешение, соотношение сторон и FOV влияют на эту проекцию. Качество теней,
текстур, сглаживания и прочие настройки рендера CS2 для каркасных тел не нужны.

## Данные helper

Во всех путях сбора игроков Linux/Windows добавлены поля, старые поля сохранены:

| Поле | Значение |
|---|---|
| `m_eye_pitch` | Вертикальный угол из первой компоненты `m_angEyeAngles`; положительный смотрит вниз |
| `m_eye_position` | Мировая позиция глаз из origin + `CNetworkViewOffsetVector` |
| `m_camera_fov` | `CCSPlayerBase_CameraServices.m_iFOV` при валидном ненулевом значении |
| `m_bounds_min`, `m_bounds_max` | Локальные границы collision-тела игрока |

Недоступные дополнительные значения передаются как `null`, а не выдумываются.
Поля камеры и collision используют существующие schema offsets; на Linux новые
необязательные offsets берутся только из живого сканирования.
Структура полей камеры соответствует
[cs2-dumper](https://github.com/a2x/cs2-dumper/blob/main/output/client_dll.hpp).

Для локального игрока используется переданная helper матрица рендера; для других
игроков — их собственные направление глаз и параметры камеры. Матрица локального
helper никогда не применяется к удалённому выбранному игроку. Повреждённая
необязательная матрица игнорируется без потери остального кадра.
Игрок за камерой не рисуется; пересекающиеся с границей обзора рёбра обрезаются
до деления на глубину. Стены и видимость не вычисляются. Каркасы обозначают
collision-тела, а не анимированную модель игрока. В режиме реконструкции camera
shake, aim punch и интерполяция перехода FOV не воспроизводятся; режим матрицы
использует камеру, фактически содержащуюся в переданном кадре рендера.
При потере связи или отсутствии свежего кадра тела скрываются.

## Задержка

Helper целится в период 1/60 секунды **вместе** со временем сбора и отправки кадра,
а не добавляет фиксированную паузу после обработки. Если сбор медленнее целевого
периода, следующий цикл начинается без дополнительного ожидания. Частота зависит
от стоимости чтения памяти и не гарантированно достигает 60 Гц.

На Linux helper предпочитает чтение через уже открытый `/proc/<pid>/mem`, чтобы
сократить накладные расходы частых небольших запросов. Если этот дескриптор
недоступен, используется резервный `process_vm_readv`. Значения читаются заново
при каждом запросе; завершение процесса передаётся механизму переподключения.

Оверлей пробуждает GTK при поступлении нового кадра; постоянный таймер используется
для состояния compositor и устаревших данных. Приёмник хранит только последний
необработанный кадр, ограничивает входную очередь WebSocket и отключает сжатие
для своего соединения. Обычное Tk-окно проверяет новые кадры каждые 8 мс и не
перерисовывает статичную сцену без необходимости.

После обновления нужно перезапустить **helper и перспективу/оверлей**, иначе
работающие процессы продолжат использовать старую частоту и старый рендерер.

## Проверки

В окружении с `requirements-dev.txt`:

```sh
python -m unittest discover -s tests -v
mypy --config-file perspective/mypy.ini
```

GUI-тест использует настоящее Tk-окно и локальный WebSocket-сервер. Нужен
`DISPLAY` (подходит XWayland); без него GUI-тест пропускается. Для нового окружения
устанавливайте зависимости в отдельный venv, не в системный Python.

Строгая проверка GTK-кода использует `PyGObject-stubs` и типы, поставляемые с Cairo.
Для установки только stubs в проверочное окружение можно использовать
`pip install --no-deps --config-settings=config=Gtk3,Gdk3 PyGObject-stubs` внутри
этого venv; это не устанавливает и не заменяет системный PyGObject.

Дополнительная проверка на реальном Hyprland запускается явно, поскольку на время
создаёт собственное полноэкранное тестовое окно. Нужны `grim` и `wlrctl`:

```sh
WEBRADAR_HYPRLAND_TEST=1 python -m unittest tests.test_overlay_native -v
```

Тест проверяет слой 3 (`OVERLAY`), изображение рамок поверх полноэкранного окна,
прозрачный фон, сохранение фокуса, реальные клики и клавиши в нижнее окно,
скрытие слоя после закрытия окна и корректное завершение. Настоящая CS2 для него
не запускается. `WEBRADAR_WLRCTL=/путь/к/wlrctl` выбирает локально подготовленный
инструмент вместо установленного. Снимок тестового экрана сохраняется в
`/tmp/codex-perspective-overlay.png`.


Windows-проверка нативного окна запускается явно на Windows:

```bat
set WEBRADAR_WINDOWS_TEST=1
python -m unittest tests.test_overlay_windows -v
```

Она использует собственное тестовое окно; запуск этой проверки на Linux
не подтверждает работу Win32-окна.
